# Runtime preparation packaging

This profile currently targets native Linux arm64 on Docker Desktop Kubernetes with user namespaces. Keep `runtimePreparation.enabled: false` and `profile.qualified: false` until the deployment's complete acceptance run succeeds. Engine qualification alone does not qualify the application pipeline.

Run `dev/scripts/runtime-preparation-images.sh <patched-linux-arm64-cli> <expected-sha256>` to build all three static MUSL binaries with the pinned Rust Alpine Dockerfile, package both images, and import them only into Docker Desktop. The script cancels its own build below ten GiB host free space. An optional third argument reuses an existing verified static binary directory. No release is modified.

The worker Dockerfile consumes three static MUSL executables from its build context: `runtime-worker` (Cargo's `ayni-orchestrator-runtime-preparation` binary), `runtime-supervisor` (`ayni-runtime-supervisor`), and `runtime-verifier` (`ayni-orchestrator-runtime-verifier`). The probe image contains only the worker installer/compatibility launcher and verifier. Dynamic executables cannot run in the scratch probe image or arbitrary candidate images.

Download the public umoci 0.6.0 `umoci.linux.arm64` release into the context; the Dockerfile verifies SHA256 `5cfd17f2e7a4bcf9ed67ea1b955ca893d200349b9ce6a3d3707dba415f458a1f`. Podman 5.8.9 and Skopeo 1.22.3 are copied from immutable public image manifests. The Ayni CLI is an explicit artifact input with a required checksum; the Dockerfile and script both verify it. This permits a reviewed patched binary without accepting an unverified download or silently using the known failing CLI. The official executor image must match the admitted lock/profile.

Build both Dockerfiles with an empty Docker configuration, explicit Docker Desktop socket, and installed Docker CLI plugin path. Import local images using `dev/lib/images.sh` and resolve their node manifest digests before setting the profile. Never set qualified merely because a local image exists. The master authority Secret belongs in the application namespace; the immutable administrator signer Secret belongs in the dedicated runtime namespace. Its name, UID and public key must match the public signer configuration. No seed is supplied in Helm values.

The tested builder settings require `hostUsers: false`, UID/GID 1000, nested user namespace mapping, VFS storage, `BUILDAH_LAYERS=false`, unmasked proc, unconfined seccomp, SETUID/SETGID helpers and permission for those helpers to elevate inside the Kubernetes user namespace. These settings exceed restricted Pod Security. No privileged container, SYS_ADMIN, host socket, host namespaces or host volume is used. Other stages retain RuntimeDefault seccomp, no elevation, and dropped capabilities; compatibility launchers alone run a trusted static UID/GID 0 parent inside the pod user namespace, with only SETUID/SETGID and no-new-privileges. They require those exact effective capabilities and drop workload children to UID/GID 10002 with no capabilities or supplementary groups. The parent is not host root; a non-root parent whose capabilities exist only in its bounding set is rejected.

The chart requests default-deny network policies. They require a functioning policy controller: the tested Desktop cluster has kindnet and kube-proxy, and its denied candidate pod still connected to the public positive-control address. That cluster is not qualified, and the profile must remain disabled until actual enforcement passes. Public stage egress is an explicit values switch allowing TCP 80/443 to public IPv4 destinations, excluding private/link-local ranges. It is not a hostname allowlist. Verification workloads have no network policy grant, API capability or mounted registry credentials; node image pull credentials are separate immutable temporary Secrets. Quality children additionally reject network syscalls through the trusted launcher.

PVC requests are scheduling/provisioning requests, not demonstrated hard filesystem quotas on Docker Desktop's local-path provisioner. The stage code bounds OCI/file I/O. Pod ephemeral storage and emptyDir limits are asynchronous kubelet eviction limits. Qualification observed a 1 MiB emptyDir overrun evicted by kubelet and confirmed that pod deletion killed the entire nested build process group and removed its emptyDir. Native Rust builds exceeded the tested 8 GiB allowance; do not advertise arbitrary Rust repositories within that profile. Preserve at least 8 GiB host free space when accepting on Desktop.

The corrected Node fixture has completed an actual worker build, independent freeze, public Ayni certification, final OCI assembly, digest-preserving local registry round trip, content verification and managed compatibility using the reviewed Podman identity fix. Wrong-signing-key, source/content tampering and unsafe parent contexts were rejected; nested cancellation removed processes and scratch storage. The overall component gate failed the network-policy negative, so it does not mark the profile qualified. A separate real-worker read-only GHCR test returned `registry_access_denied` with deliberately invalid synthetic credentials. These results do not establish GitHub acquisition, live GHCR publication, control-plane admission or supervisor restart recovery. The reusable qualification driver records each invocation's coverage and exclusions in its JSON result.

## Supervisor lifecycle qualification

Run `python3 dev/scripts/runtime-supervisor-qualify.py --self-test` for the synthetic authority's protocol checks, then `python3 dev/scripts/runtime-supervisor-qualify.py --worker-image <immutable-local-worker-reference>` to exercise the actual supervisor on the explicit `docker-desktop` context. The driver owns and removes a unique namespace, uses synthetic credentials and namespace-only RBAC, and records public evidence in `/tmp/ayni-runtime-supervisor-qualification.json`.

The lifecycle test holds cleanup reports, replaces the supervisor Pod, checks that the cleanup Pod keeps its exact UID, and verifies deletion of operation-owned Pods, PVCs and Secrets while unrelated resources remain. It accepts the final stopped acknowledgement only after the driver observes that exact cleanup Pod absent. Its in-memory HTTP authority is a fixture: PostgreSQL fencing, real control-plane admission, the Helm deployment, registry access and NetworkPolicy enforcement require their separate gates. A lifecycle pass cannot enable or qualify the complete deployment profile.
